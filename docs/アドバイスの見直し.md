# 改善アドバイス（F23）の見直し手順（月 1 回）

要件 04 の 6 章に沿った手順。Claude Code の定期実行（Routine）が毎月 26 日（給料日基準の月が締まった翌々日）にこの手順で動き、変更案をプルリクエストで出す。公開（main へのマージ）は本人の承認後。

## 守ること

- 使うのは **管理者（本人）の記録と反応だけ**。本人の user_id は Supabase の `private.app_config`（`owner_user_id`）にある。知人の記録・反応は本人の同意なしに使わない
- 家計の数字・集計結果はリポジトリ・プルリクエストの本文に書かない（「食費のしきい値を上げる」のように、ルールとしきい値の話だけにする）
- 直すのは `src/lib/adviceRules.ts` だけ（月の気づきの `LIMITS` / `RULES`、今日の気づきの `DAILY_LIMITS` / `DAILY_RULES`、文言、ルールの追加・削除）。ルールの ID（`rule`）は集計に使うので、意味が変わらない限り変えない

## 手順

1. `SUPABASE_PROJECT_REF=<ref> node scripts/advice-review.mjs /tmp/advice-review.json` で集計する（出力はリポジトリの外に置く）
2. 見ること
   - ルールごとの「役に立った / 立たない」。立たないが多いルールは、しきい値を厳しくするか文言を変えるか、やめる
   - 直近の反応の文言（`recent.title`）。どの言い方が役に立ったか
   - 期間ごとの大分類別の変動費（`variable_by_period`）。今のルールで拾えていない増え方・使い方がないか
   - 本人の返済計画（リボの一括返済の予定）と、黒字化の目標（要件 01）に近づいているか
3. 変更案を `src/lib/adviceRules.ts` に入れ、`tests/unit/advice.test.ts` にそのルールのテストを足す（数字は作り物を使う）
4. `npm run typecheck && npm run test:unit && npm run test:e2e` を通す
5. ブランチを切ってプルリクエストを出す。本文には「何を・なぜ変えたか」をルールとしきい値の言葉で書く（金額は書かない）
6. 変更がない月は、プルリクエストを出さずに終わる

## 反応がまだ少ないうち

反応が 1 つのルールにつき数件たまるまでは、しきい値を大きく動かさない。ルールが出ていない（反応がない）のは「問題がない」可能性もある。
