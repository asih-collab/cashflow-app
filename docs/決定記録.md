# 決定記録

作業の中で決めたこと・変えたことを新しい順に残す。要件そのものの変更は、非公開リポジトリ側の各ドキュメントの「決定事項と理由」にも書く。

## 2026-10-29 ホームの予算: 予算のない大分類もマイナスで出し、マイナスは赤で（利用者の要望）

| 決定 | 理由 |
|---|---|
| 予算のない大分類（例: 特別な支出）は予算 0 円として、使った分を「−¥◯」で出す。説明は「予算なし · 全体の残りから引いています」 | 全体の「あと使える」からは引いているのに、一覧ではプラスに見えて紛らわしかった |
| マイナスの数字（大分類の残り、ホームの予算超過）は赤（`--neg`）にする | アクセントの橙と区別し、超えたものがひと目で分かるように |

## 2026-10-28 今日の気づきを「画面にない、節約に効くこと」に絞る（利用者の要望）

| 決定 | 理由 |
|---|---|
| 「今日使えるのはあと◯円」は、目安を超えたときだけ出す（注意と、残りの日の 1 日あたり） | 目安の内なら、ホームの「あと使える」「1 日あたり」と同じ数字で、気づきにならない |
| 目安の計算で、先の日付で記録した変動費（予定）も先に引く | ホームの 1 日あたりと数字が食い違っていた |
| 追加: 習慣の出費（この 30 日で 6 回以上・1 回平均 3,000 円以下のものを今日また使ったら、1 年に直した額と「週 1 回減らすと年◯円」） | 小さな出費の積み重ねは、1 回の額では重さが分からない。使ったその日に、減らしたときの効果まで見せる |
| 追加: 使わない日（昨日 0 円なら、今月何日目かと「週にもう 1 日増やすと月◯円」） | 我慢ではなく、できたことを褒めて続けてもらう |
| 追加: 明日が使いすぎやすい曜日なら前の日に知らせる | 当日より、前の日のうちに上限を決めるほうが守りやすい |

## 2026-10-26 レシートをアプリ内のカメラで読み取る（利用者の要望「カメラロールがレシートで埋まるのが嫌」）

| 決定 | 理由 |
|---|---|
| レシート画面の主な操作を「カメラで撮る」にする。`<input capture>` で撮った画像は保存されず、この端末の中で文字にして捨てる | カメラロールに残さないため。ブラウザ（ホーム画面のアプリ）からは iPhone の文字認識を呼べないので、アプリに文字認識を持たせる |
| 文字認識は Tesseract（tesseract.js 7.0.0、日本語の小さいモデル best_int 約 2MB + 本体約 3MB）。部品は自前で配信し（`scripts/copy-ocr.mjs` → `dist/ocr/`）、最初に使ったときだけ読み込んで Service Worker の別キャッシュに残す。起動時の先読みには入れない | 費用ゼロで画像を外に出さない（05 の制約）。外部の文字認識（Google Cloud Vision や AI）は精度は上だが、画像を外に送り、鍵と支払い設定が必要 |
| 画像を整えてから読む（大きさをそろえ、白黒にし、まわりの明るさとの差で文字を浮かせる）。整えた画像とそのままの画像の 2 回読み、両方の手がかりを合わせる | 片方だけに出る読み違いを、辻つまの合う金額（お預り − お釣りなど）で打ち消す |
| 読み取り側に、カメラの文字認識の読み違い対策を足した: ¥ の直後の余計な 1 文字、¥ が似た字（寺・半など）になる、桁区切りの後の空白、日付の数字の読み違い（9→0 など。最近の日付になる候補を選ぶ） | 実際に画像で試して多かった誤り |
| 精度（作り物のレシート 40 枚を画像にして測定。ブラウザでの実際の処理）: 鮮明な写真で合計 37/40（約 93%）、日付 38/40（95%）。かなりぼやけた・影のある写真では合計 11/40 だが、そのうち 28 枚は「要確認」と出る | アプリ内のカメラは写真の写りで精度が大きく変わる。撮り方のコツと「撮り直す」を出す。より正確にしたい場合は iPhone の文字認識（ショートカット）を案内する |
